# 问题分级、置信度与证据【可选，已启用】
在确定问题分级、判断证据充分性或划分安全审计边界时读取本文件。

## 严重程度
- critical：在现实触发条件下可能造成严重数据损失、权限失守、广泛安全事件或核心服务不可用，需要立即阻断合并或发布。
- high：主要功能在常见路径失败、造成重要数据错误或明显安全/兼容性破坏，通常应在合并或发布前修复。
- medium：特定但现实的条件下可复现错误，或能说明实际影响的性能、测试、兼容性或维护风险。
- low：影响有限但真实存在的问题；不得用 low 收纳没有实际影响的个人风格偏好。

级别必须同时说明触发条件、影响范围和用户或工程后果。证据不确定时降低置信度，而不是夸大严重程度。

## 置信度
- high：代码路径、契约及反证均已核实，并有可执行复现、失败测试或等价的直接证据。
- medium：静态路径和影响闭合，但因环境限制未能实际执行，或仍存在较小的未核实前提。
- low：存在合理风险线索但缺少关键条件；通常应列入“待验证疑点”，而不是确认问题。

## 证据规则
- executed：由本 Agent 在当前任务中实际执行并观察到的结果，记录命令、关键输出和环境前提。
- static：由代码、配置、契约或差异静态推导，说明调用路径、输入约束和为何现有防护不足。
- reported：来自用户、实现者或外部报告，必须标明来源；未经独立核实不能伪装为 executed。

每个确认问题至少具有 static 或 executed 证据，并检查不可达条件、调用方校验、平台约束、已有测试等反证。仅凭“可能”“最佳实践”或工具告警不得直接认定缺陷。

## 质量边界
- 基础安全检查包括明显的输入信任、权限校验、敏感信息暴露、不安全默认值及已知危险用法。
- 威胁建模、漏洞利用、主动扫描、凭据审计、供应链取证和合规认证属于安全专职工作；发现需要时说明具体移交目标，不自行扩展。
- 可维护性问题必须说明可观察的修改风险、错误概率、验证困难或维护成本；纯命名、排版和个人风格意见单列为可选建议或省略。
- 性能问题必须说明输入规模、复杂度、热路径或测量证据，不能仅凭局部写法推断用户可感知退化。
