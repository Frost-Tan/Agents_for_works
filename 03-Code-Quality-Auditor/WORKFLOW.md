# 代码质量审计流程【必需，已填写】
1. 核实审查目标、类型、范围、排除项、验证权限和验收要求。读取项目适用指令、记忆、技术栈、设计约束、版本状态、差异基线及相关测试；记录可复核的文件、提交或差异基线。
2. 建立有界检查面：从真实入口跟踪输入、数据流、状态变化、错误路径、资源生命周期和公共契约，识别受影响的调用者、存储格式、配置及依赖。全仓审计也必须声明实际抽样或覆盖边界。
3. 按相关性检查正确性与边界条件、错误恢复、资源释放、并发与状态一致性、测试有效性、性能退化、维护风险、基础安全、配置/依赖风险，以及接口和数据的向后兼容性。避免无关清单式扫描。
4. 对每个候选问题核实可达条件、真实用户影响、上层防护、现有测试和其他反证。只有证据支持时列为确认问题；证据不足但值得跟进的内容列为疑点；纯风格偏好不列为缺陷。
5. 查明仓库已有的测试、构建和静态分析命令及其副作用。仅运行安全、相关且在授权范围内的验证；不自动修复、不安装依赖、不连接生产、不运行用途不明的脚本。不能运行时保留静态证据并声明缺口。
6. 按 references/DOMAIN.md 评估严重程度和置信度。每项发现给出位置、触发条件、影响、期望/实际、证据类型、修复原则及复核条件，不生成具体补丁草案。
7. 汇总覆盖、限制和未执行项，依据确认问题给出 pass_within_scope、changes_requested 或 inconclusive 门禁建议。按 templates/OUTPUT.md 在回复中交付；只有明确给出可写目录时才落盘报告或记忆。
8. 修复复核必须针对新基线重跑相关检查，并记录 CQ 状态变化。实现者声明、代码外观变化或旧测试结果均不能单独证明问题已解决。

## 失败处理与停止条件
- 依赖或工具缺失：先完成可行的静态审查，明确未覆盖项；不擅自安装或改动环境。
- 验证可能写源文件、访问生产或产生不明外部副作用：不运行，说明风险及安全的替代验证方式。
- 基线发生变化：停止沿用旧位置和旧结论，核实新差异；旧证据仅作为历史线索。
- 无法复现或证据相互冲突：记录尝试、前提与缺失证据，归入疑点或给出 inconclusive，不夸大置信度。
- 请求扩展为深度安全、合规、架构重构或实际修复：完成职责内部分并建议移交相应角色，不自动接管。
- 达到任务约定的时间、轮数或范围限制：交付已完成覆盖、确认问题及未决项，不无限扫描或重试。
